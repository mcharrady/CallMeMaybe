# Call Me Maybe

## Description

**Call Me Maybe** is a Python project focused on introducing **function calling in Large Language Models (LLMs)**.

The goal of the project is to transform a natural-language user request into a structured function call. The generated call contains:

* The original user prompt
* The selected function name
* The parameters required by that function
* Parameter values extracted from the user's request

The project uses a language model through `llm_sdk.Small_LLM_Model` and applies **constrained decoding** to control the tokens generated by the model.

The implementation separates the process into two main stages:

1. **Function selection** — the model selects the function that best matches the user's request.
2. **Parameter generation** — after the function is selected, the model generates the parameters while following the function's expected JSON structure and parameter types.

Pydantic models are used to represent and validate the input data, function definitions, and generated function calls.

## Algorithm Explanation

The main algorithm is based on **constrained decoding**.

Instead of allowing the language model to generate any token, the implementation determines which tokens are valid at each generation step and selects the highest-scoring token among those valid choices.

### 1. Input parsing

The program first reads two JSON files:

* A file containing the user prompts
* A file containing the available function definitions

The parser converts the JSON data into Pydantic models:

* `Prompt`
* `FunctionDef`
* `ParaSchema`

The parser also checks for invalid conditions such as duplicate JSON keys and duplicate function names.

### 2. Function selection

Each available function name is encoded into a sequence of model token IDs.

For example, conceptually:

```text
fn_add_numbers
        ↓
[token_1, token_2, token_3, ...]
```

The generator stores the encoded token sequence for every available function.

During generation, the current token sequence is called **progress**.

Only functions whose encoded names still match the current progress are considered possible.

For example, if the available functions were:

```text
fn_add
fn_average
fn_subtract
```

the decoder restricts the next token to tokens that can continue one of the remaining function names.

The model's logits are then used to choose the highest-scoring token among those valid candidates.

This process continues until the generated token sequence exactly matches one function name.

Therefore, the model is still responsible for choosing the function, but the decoder prevents it from generating a function name that is not present in the provided function definitions.

### 3. Building the JSON skeleton

Once the function has been selected, the decoder creates a JSON skeleton based on its definition.

For example, a function with:

```text
a: number
b: number
```

produces a conceptual structure similar to:

```text
{
    "a": number,
    "b": number
}
```

The JSON structure itself is encoded into token IDs, while the values are represented by their `ValType`.

This creates a generation plan containing both:

* Fixed structural tokens
* Value types that still need to be generated

### 4. Constrained parameter generation

The generator then asks the model to produce the parameter values.

For structural parts of the JSON object, the required token IDs are inserted directly according to the skeleton.

For parameter values, the decoder calculates a set of valid token IDs based on the expected type.

#### Strings

String generation is restricted using the model vocabulary.

The implementation:

* Identifies quote tokens
* Builds a vocabulary of tokens that can safely occur inside strings
* Excludes tokens containing quotes, backslashes, braces, and non-printable characters
* Restricts string generation when a string becomes too long or repetitive

Regular-expression parameters receive additional restrictions so that certain regex-ending characters can cause the string to terminate.

#### Booleans

Boolean values are restricted to the two JSON boolean literals:

```text
true
false
```

The decoder only allows tokens that continue one of these two possible values.

#### Numbers

Numbers are generated using a restricted set of characters:

```text
0123456789.-e+
```

The decoder controls which of these characters can be generated depending on the current number buffer.

This allows the generation of integer and floating-point-style numeric values, including scientific notation for `number` values.

### 5. Selecting the highest-scoring valid token

At every constrained generation step, the model produces logits for the vocabulary.

The implementation does not allow an arbitrary token to be selected.

Instead, it receives a set of allowed token IDs and chooses the token with the highest logit among that set.

Conceptually:

```text
Model logits
     ↓
Valid token constraints
     ↓
Allowed tokens only
     ↓
Highest-scoring allowed token
     ↓
Next generated token
```

This provides deterministic structural control while still using the language model's predictions to determine the content.

### 6. Final validation

After parameter generation, the generated text is parsed using `json.loads()`.

Numeric `number` values are converted to Python `float` values.

The resulting `FunCall` is then validated against the selected `FunctionDef`.

The validator checks:

* The generated function name
* The exact set of parameters
* The type of every parameter

If the generated function call does not match the expected definition, an exception is raised.

## Design Decisions

### Pydantic for data validation

Pydantic is used for the project's data models.

The main models are:

* `Prompt`
* `ParaSchema`
* `FunctionDef`
* `FunCall`

This provides structured validation for JSON input and generated function calls.

Extra fields are forbidden for several models to prevent unexpected data from being accepted.

### Two-stage generation

Function selection and parameter generation are separated.

The first stage determines which function should be called.

The second stage generates the parameters for that specific function.

This allows parameter generation to use the selected function's schema as a constraint.

### Schema-driven generation

The JSON structure is generated from the selected function definition rather than being freely generated by the model.

This ensures that the expected parameter names and their order are determined by the function definition.

### Token-level constraints

The implementation operates directly on token IDs returned by the model.

This allows constraints to be applied during generation rather than trying to repair invalid output afterward.

### Caching

Token information that is expensive to construct is cached.

The implementation caches:

* Character-to-token mappings used for numbers
* String vocabulary information

This avoids rebuilding the same information repeatedly.

### Final validation

Even though generation is constrained, the final result is still validated.

This provides an additional layer of reliability before a result is written to the output file.

## Performance Analysis

### Accuracy

The project is designed to correctly select the appropriate function and extract its parameters from natural-language prompts.

Function selection is constrained to the functions supplied in the function-definition file.

Parameter generation is constrained according to the selected function's parameter types.

The project requirements target **90% or higher correctness** for function selection and argument extraction.

### Speed

The generation process performs token-by-token constrained decoding.

For every generated token, the model produces logits and the decoder determines the valid tokens.

Caching is used for repeated token information to reduce unnecessary work.

The project requirements specify that the tests should complete within **5 minutes on standard hardware**.

### Reliability

Reliability is improved through several layers:

1. Input validation with Pydantic
2. Duplicate-key detection
3. Duplicate-function detection
4. Constrained function selection
5. Type-specific parameter constraints
6. JSON parsing of the generated parameters
7. Final function-call validation
8. Exception handling in the program entry point

## Challenges Faced

### Restricting function selection

A language model normally has access to a large vocabulary and can generate arbitrary text.

The challenge was to allow the model to choose a function while preventing it from producing a function name that does not exist.

This was addressed by encoding every available function name and allowing only tokens that remain compatible with at least one candidate function.

### Generating valid structured parameters

Generating free-form JSON with an LLM can result in invalid JSON or incorrect parameter types.

The solution was to create a generation skeleton from the selected function definition and constrain value generation according to the expected parameter type.

### String generation

Strings are more difficult to constrain than simple numbers or booleans because many vocabulary tokens can contain arbitrary text or JSON-special characters.

The implementation therefore constructs a usable string vocabulary and excludes problematic tokens.

### Numeric generation

Numbers require different restrictions depending on the current state of the number.

The decoder therefore keeps track of the current number buffer and determines which numeric characters can legally continue it.

## Input and Output

### Input

The program receives:

1. A JSON file containing prompts.

Example:

```json
  {
    "prompt": "What is the sum of 2 and 3?"
  }
```

2. A JSON file containing function definitions.

Function definitions contain information such as:

* Function name
* Description
* Parameters
* Parameter types
* Return type

Example:

```json
  {
    "name": "fn_add_numbers",
    "description": "Add two numbers together and return their sum.",
    "parameters": {
      "a": {
        "type": "number"
      },
      "b": {
        "type": "number"
      }
    },
    "returns": {
      "type": "number"
    }
  }
```

### Output

The program writes a JSON array containing function calls.

For example:

```json
  {
    "prompt": "What is the sum of 2 and 3?",
    "name": "fn_add_numbers",
    "parameters": {
      "a": 2.0,
      "b": 3.0
    }
  }
```

The output therefore represents the structured interpretation of the original natural-language request.

## Conclusion

Call Me Maybe demonstrates how a language model can be combined with deterministic constraints to transform natural-language requests into structured function calls.

The central idea is to let the language model provide the semantic decision-making while using constrained decoding to control the structure and validity of the generated result.

The project therefore combines:

* LLM inference
* Token-level generation
* Constrained decoding
* JSON generation
* Pydantic validation
* Command-line execution
* Error handling
